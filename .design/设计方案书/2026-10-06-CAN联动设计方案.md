# 底盘 CAN v3 首轮联动设计方案

- 日期：2026-10-06
- 状态：已确认，执行中
- 范围：单块 C30D 底盘板与 Jetson Orin Nano 的首轮 CAN 联动

## 1. 目标与边界

使用经典 CAN 2.0A、1 Mbps 和 CAN v3，先建立单底盘板与 Orin 上位机之间的可观测、可控联动。首轮沿用下位机已有的体速度接口，不将其误认为后续 `ros2_control` 的轮速接口。

首轮只覆盖底盘，不覆盖机械臂、夹爪、UART v2 或完整 `ros2_control` 硬件接口。验证按“代码与协议核对 → 被动收帧 → 烧录确认 → 另行授权后低速点动”逐级进行。当前批准不包含烧录、发送 `START` 或电机运动。

## 2. 当前依据

- 下位机当前主线为 `3ecdb93`（R21），已合入 R20 CubeMX/HAL 迁移；CAN v3 接收 `0x010 SAFETY_CMD`、`0x100 CHASSIS_VEL_CMD`，发送 `0x200 CHASSIS_VEL_FB` 和 `0x230 NODE_INFO_CHASSIS`。
- 下位机 `docs/PROTOCOL.md` 与 `tools/can_check.py` 是 CAN v3 的协议依据；R21 主线的协议校验、CubeMX 门禁及 Debug/Release 构建命令均已通过，当前构建工具报告无待重编目标。
- 当前固件没有发送 `0x201 CHASSIS_DIAG`；Orin 节点虽然能解码该帧，但本阶段不把它列为双向基础通信的验收条件，也不在没有明确状态位/故障码映射的情况下自行补定义。
- Orin 的 `rak_can_driver` 已实现 SocketCAN CAN v3 底盘节点。节点默认 `initial_enable=false`，将 ROS `Twist` 转换为 `0x100`，解析底盘反馈，并通过安全服务发送 `0x010`。
- Orin 最近检查时 `can0` 处于 DOWN，错误计数为零。用户已确认 CAN 硬件侧准备就绪；执行联测前仍须复查状态，按经典 CAN 2.0A、1 Mbps、CAN FD 关闭的合同配置接口。
- Orin 的 `~/rak` 位于 `e58a8ed`，包含已提交的 CAN 驱动；工作树另有相机相关修改和未跟踪文件。本机 `rak` 工作树干净，当前 `main` 落后远端 33 个提交且可快进。同步时只快进本机工作树，不改写 Orin 未提交内容。
- Orin CAN 编解码测试已通过 14 项；运行测试需将 `~/rak/src/rak_can_driver` 加入 `PYTHONPATH`。
- Orin 同时有 UART v2 规范，但该规范要求的 F407 v2 端点尚未集成。本阶段明确使用 CAN v3，不把 UART v2 与 CAN v3 混用。

## 3. 链路与职责

### Jetson Orin Nano

- Linux `can0` 使用 mttcan 控制器，外接 SN65HVD230 收发器。
- ROS 侧使用 `rak_can_driver`：100 Hz 发送 `0x100`，接收底盘状态与诊断帧。
- `initial_enable` 保持关闭。正常启动节点只发送禁用的零速帧；任何使能或非零速度测试均须单独授权。

### C30D 下位机

- 使用板载 CAN 收发器和 CAN1 的 PD0/PD1，不在 MCU 侧增加第二个 CAN 收发器。
- 沿用现有 CAN v3 编解码、安全状态与速度控制，不在本阶段改动控制行为或外设配置。
- 上电时底盘控制状态为 IDLE；电机 PWM 可以启动，但未收到有效使能前不得产生驱动目标。
- 当前固件会在启动任务中扫动 PC6 舵机通道。首次上电前应断开舵机负载或固定机构，避免将该自检运动误判为底盘控制。

### 物理总线

- 传输限定为经典 CAN 2.0A，11 位标准帧，1 Mbps；禁止 CAN FD。
- 总线两端各有一个 120 Ω 终端，中间节点不额外并联终端；Orin 与底盘地线共地。
- 首轮联测前只检查接线、终端和接口状态，不在未确认当前状态时执行会改变接口配置的命令。

## 4. 分阶段验证

### 阶段 A：软件与仓库对齐

1. 再检查本机 `rak` 工作树干净及 Orin 未提交文件清单。
2. 本机 `rak/main` 使用 `git merge --ff-only origin/main` 快进至已确认的 `e58a8ed`，不对 Orin 执行同步写入。
3. 保留 Orin 上所有未提交、未跟踪内容；不运行 `reset`、`clean`、覆盖式 checkout，也不自动提交或推送。
4. 确认 CAN 编解码与下位机 golden vector 一致，且上下位机使用同一 CAN v3 合同。

### 阶段 B：接口与被动验收

1. 检查 Orin `can0` 的 UP/DOWN、速率、CAN FD 状态、bus-off 与错误计数；当前 DOWN 时配置为经典 CAN、1 Mbps、CAN FD 关闭并启动接口。
2. 在下位机未使能、动力电源关闭或电机负载安全隔离的条件下，被动观察底盘 `0x200` 状态帧与 `0x230` 节点信息帧。
3. 使用默认禁用的上位机节点发送零速 `0x100`，在总线上确认该帧到达下位机；确认底盘继续回传可解码的 `0x200`/`0x230`，并在 ROS 侧看到 `/chassis/measured_twist` 更新。
4. 核对帧 ID、DLC、CRC、计数器、R21 节点版本及状态，不发送 `START` 或非零速度。
5. 发现错误帧、bus-off、无下行帧、无上行反馈、构建版本不符或帧内容不符时，停止推进并先定位物理层、时钟、位时序或协议问题。

### 阶段 C：烧录验收

本阶段须在用户另行确认后执行。烧录前确认轮子架空、动力端子断开，并处理 PC6 舵机启动扫动；烧录后执行规定的真断电冷启动，通过 OLED 的 `build_tag` 确认实际运行版本。未看到 `R21` 前不进入联动。

### 阶段 D：受控低速点动

本阶段须再次单独确认。仅在 CAN 被动验收通过、车轮架空、物理使能条件受控且急停可触及时进行。先验证 STOP 与链路中断后的看门狗行为，再仅给 `Vx`、`Vy`、`Wz` 三个机体速度分量中的一个发送最小幅值，另两个分量保持为零；确认方向、反馈和停止行为正确后才扩大测试范围。测试中出现不出扭矩、失控、急停异常、bus-off 或错误计数增长时，立即停止，不擅自修改 25 kHz 控制频率。

## 5. 验收标准

- 本机协议门禁、CubeMX 门禁和 Debug/Release 构建通过；当前结果可作为软件基线。
- 上下位机 CAN v3 测试向量逐字节一致。
- 被动验收阶段能稳定识别底盘节点与状态帧，CRC、帧 ID 和 DLC 正确。
- 约定的连续观测窗口内，bus-off、接收错误和发送错误计数不增长；长时压力验收采用协议文档建议的 10 分钟窗口。
- 双向基础通信阶段看到上位机 `0x100` 与底盘 `0x200`/`0x230`，协议解析正确，且 CAN 错误计数不增长。
- 烧录阶段通过 `R21` 构建标签确认；低速点动阶段必须证明禁用状态不驱动、显式使能才允许运动、STOP 和链路超时能使底盘按固件行为停止。

## 6. 风险与明确不做的事项

- Orin 上的 CAN 节点仍是实验室原型，ROS 控制主题和安全服务没有认证。本阶段只在受信任的本机 ROS 环境使用，不将安全服务暴露给不受信任的网络。
- CAN v3 的底盘命令仍是体速度语义；本阶段不声称满足 UART v2 的四轮角速度及关节位置合同。
- 不接入或校准机械臂与夹爪，不扩展舵机通道，不更改 25 kHz 频率、CAN 位时序或 CubeMX 外设配置。
- 不在本阶段改写用户已有的 Orin 文件，不自动烧录，不发使能命令，不执行实车行驶。
- Orin `can0` 的运行状态可能已在上次检查后变化；操作前复查是强制检查项，而不是假定它仍然 DOWN。

## 7. 下一步门槛

本方案已获确认。先执行阶段 A 的只读仓库核对与阶段 B 的禁用零速双向验收。阶段 C 烧录和阶段 D 电机点动仍分别等待用户明确确认。
