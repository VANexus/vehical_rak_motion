# 已知问题：左前轮 `allow_motion=true` 后自转不停
> 轮序/方向/标定常数以 `Core/Inc/wheel_config.h` 为准；本文只记录现象与结论。



> 来源：GitHub issue **VANexus/rak#8** —《[底盘] allow_motion=true 后左前轮自转不停
> （累计 ≈233 圈），只有断电才停》。首次报告 2026-10-17，固件 `build_tag=R63`。
> 本文件是**固件侧**的读码分析 + 明天的现场取证步骤，供 CAN 联调时按序排查。
> **问题尚未定位、也未被本仓代码修复**——本文件不改变任何固件行为。

## 现象（摘）

- `chassis_bringup.launch.py allow_motion:=true` 后，**左前轮（front_left / 电机 A）持续自转**，
  累计 ≈ −1464 rad（≈233 圈），**整车断电才停**；另外三轮不动。
- 同一套 `can0` 链路的其它功能正常（能读转速、电池、舵机角）。
- F407 自报 `FAULT=0`、`STATE=0`。

## 固件侧结论：**零指令时，固件没有"自己驱动"的通路**

按当前 `R64` 代码逐条核（`Core/Src/app_car.c` / `app_car_safety.h`）：

| 路径 | 零指令时的行为 | 代码位置 |
| --- | --- | --- |
| 未标定轮（`encoder_sign==0`）且目标为 0 | `phase_drive` 被强制清 0 → 驱动门输出 **BRAKE**（两输入高） | `car_control_isr()`：`if (encoder_sign[i]==0 && v_cmd[i]==0) phase_drive=0`；`car_motor_output_gate()`：`drive_phase==0` → `CAR_MOTOR_OUTPUT_BRAKE` |
| 已标定轮、目标为 0、PI 稳态 | `v_ramp` 斜坡到 0，`duty_q` 收敛到 ~0 → 驱动门 `DRIVE` 但 `duty_percent≈0`（≈滑行） | `car_control_isr()` 1 ms 段的 PI + 斜坡 |
| 急停锁存 | `brake_all()` + 全部目标/占空比清零 | 同上 |
| kick 开环踢动 | **只在"该轮有非零目标"时**触发；零目标永不 kick | `car_control_isr()` R34 注释；`car_control_inputs_allowed()` |

也就是说：**一条非零轮速目标都收不到时，固件要么 BRAKE、要么 ~0 占空比滑行，不会主动加速。**

## 两个怀疑方向（与 issue 一致）

### 方向 A（怀疑度最高）：功率级硬件——某根 AT8236 输入线对地短路

板载 AT8236 是**双输入**（无 STBY）；`IN1=IN2=1` = 动态刹车（电机两端短接），`IN1=IN2=0` = 滑行。
若左前那一路某一根输入线**对地短路**，固件发"刹车"时芯片实际收到"一高一低" → **全速正转**。
此时固件"以为自己在刹车"，`FAULT` 自然为 0（**全板无电流采样、无故障回读**）。

- 与该现象吻合：只有断电才停（软件压不住被短路的输入线）、另外三轮正常、`FAULT=0`。
- 但**不能解释** `STATE=0`：若上位机确实在发帧，`STATE.bit1`（远程门）应为 1；
  若当时一帧没发，100 ms 后 `STATE.bit3`（cmd_stale）应为 1。→ **那次读到的 `STATE` 很可能不是轮子正在转的同一时刻**，需复现时同步抓。

### 方向 B：编码器极性反 → 闭环正反馈（有前科）

`encoder_sign` 反了 → PI 把"往前转"当成"往后转" → 反向加大油门 → 卡 85% → 飞到断电。
但要注意：本固件有**自愈**——`encoder_sign != 0 && duty_q > 40% && 方向矛盾` 时自动翻转极性
（`car_control_isr()` 附近），所以**长时飞车与该自愈路径矛盾**；除非自愈条件始终不满足
（例如编码器根本没在计数）。→ 方向 B 的可能性因此**低于方向 A**。

## 明天现场取证步骤（按顺序，轮子必须架空、手放在总电源开关上）

1. **复现并同步抓 CAN 遥测**（`can0`，1 Mbps）：
   ```bash
   candump can0,220:7FF      # 0x220 DIAG：STATE 位图 + MODE（10 Hz）
   candump can0,202:7FF      # 0x202 WHEEL_SPD：四轮实测转速
   ```
   判读：
   - `STATE` bit6-10（驱动门各环节）有 0 → 命令没落地 → **方向 A**；
   - bit6-10 全 1 → 固件在驱动 → **方向 B**；
   - `0x202` 里左前轮报大速度 → 编码器正常、固件看得到 → 更支持 B。
2. **安全默认档反证**：`ros2 launch rak_bringup chassis_bringup.launch.py`（默认 `allow_motion:=false`）。
   照转 → 与命令无关 → **方向 A**；不转 → 与命令有关 → **方向 B**。
3. **ST-Link 读内部变量**（`app_car.c`，用本机重编的带符号 `.elf`）：
   | 变量 | 判读 |
   | --- | --- |
   | `duty_q[0]` | ≈0 但轮子在转 → **硬件**；接近 ±8500 → **软件** |
   | `v_cmd[0]` | 非零 → 确实有命令 |
   | `encoder_sign[0]` | 与另外三轮不同符号 → 可疑 |
4. **（需断电）对调左前 / 右前电机线**：问题跟着电机走 → 电机/线；问题留在左前位置 → **驱动芯片**。

## 建议的固件侧后续（**尚未实现**，待裁决后再动）

- **"零指令却在转"检测**：`phase_drive==0`（BRAKE）或 `duty_percent≈0` 期间，若某轮编码器
  连续 ≥N ms 报出超过阈值的转速 → 置一个故障位/遥测标记，让"软件没在驱动但轮子在转"
  变成 **CAN 上可见**，而不是 `FAULT=0`。
  - ⚠️ 该故障位若进协议 `STATE`/`FAULT_CODE` 枚举 = **协议改动**（v4 已 FROZEN），
    必须走 YAML→两端实现→`can_check.py`→两仓同批提交的提案流程；**且要避免误报干扰明天的联调**，
    建议先用 SWD/OLED 侧标记（不进协议）验证阈值。
- 方向 A 若实锤 → 属**硬件故障**，固件无能为力；窗口期用"人工对调线/换驱动"定位并上报。

## 安全提醒

⚠️ **这是会自己动的轮子。**
- 排查时四个轮子必须垫起，手放在总电源开关上；
- 臂无本地急停，断电是唯一手段；
- 不要在人手靠近轮子时上电。
