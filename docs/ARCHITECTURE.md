## 1. 三个节点与职责边界

| 节点 | 硬件 | 职责 | 明确**不做**的事 |
| --- | --- | --- | --- |
| **Jetson（上位机，仓 ``../rak``（路径在工作区根，本仓不包含））** | Orin Nano；SLAM 建图 + Nav2 + MoveIt；**激光雷达、深度相机、IMU（ST LSM6DSRTR，SPI 直连）全部在 Jetson**；CAN = 板载 mttcan `can0` + **外接收发器模块** | 感知、定位、规划、IK，100 Hz 下发指令 | 不做电机闭环；不碰 25 kHz 时序 |
| **底盘 F407**（``../vehical_rak_chassis``（路径在工作区根，本仓不包含）） | **C30D：板载 4 路 AT8236 + 板载 CAN 收发器（PD0/PD1）**；4× MG513P30_12V（30:1、带编码器）+ 4 麦轮；调试串口 USART1(PA9/PA10) | 麦轮逆运动学 → 四轮 **25 kHz 硬实时速度闭环**；100 Hz 回报实测体速度 | 不做导航；姿态/航向融合归 Jetson |
| **机械臂 F407**（``../vehical_rak_arm``（路径在工作区根，本仓不包含）） | **与底盘完全同一块 C30D**（用户确认：两板硬件一致，只是角色不同）；4× 同型号闭环关节电机 + **1× 底座旋转步进（脉冲+方向，外接驱动器，落在 PC6=TIM8_CH1）** | 收 MoveIt 的关节目标 → **25 kHz 硬实时闭环**（位置外环+速度内环）；步进走 1 kHz 位置环 | **不做 IK**（正解在 MoveIt）；不做导航 |

关键结论：

1. **两块叶子板硬件完全相同** → 板级头文件事实上同源，L1/L2/L4/L5 可 100 % 共用（这是 `platform/` 决策的硬依据）。差异只在角色：底盘跑麦轮 IK，臂跑关节轨迹。
2. **IMU 归 Jetson**（LSM6DSRTR）。但板上还有一颗 ICM20948（PB10/11/12）——**谁是航向/里程计的权威源待定**（见 [`protocol.md`](PROTOCOL.md) §10）。
3. **IK / 轨迹规划 / SLAM / Nav2 全部在 Jetson**。机械臂固件是执行器，不是规划器；它比底盘少一层运动学、多一层轨迹插值与限位兜底。
4. **板上没有电流采样通道** → 草案里的"电流保护/过流检测"没有硬件基础；堵转改用软件判据（占空比高 + 编码器不动）。

## 2. 通信拓扑与频率预算

```
                  CAN 总线 1 Mbps・CAN 2.0A・单条总线三节点
   Jetson ────┬────────────┬──── 100 Hz：0x100 底盘速度 / 0x101+0x102 臂关节
              │            │     事件：0x010 安全命令（广播）
        底盘 F407 ─── 0x030/0x031 ─── 机械臂 F407      1 kHz：两板互锁
              │            │     100 Hz：0x200/0x210 反馈，0x201/0x212 诊断
              └─ 0x020/0x021 EMCY（事件，高优先级）─┘
```

**完整帧表、字节布局、超时与故障码在 [`protocol.md`](PROTOCOL.md)，本表只留频率骨架**：

| 链路 | 频率 | 帧（v3 ID） |
| --- | --- | --- |
| Jetson → 底盘 | 100 Hz | `0x100 CHASSIS_VEL_CMD` |
| Jetson → 机械臂 | 100 Hz | `0x101 ARM_JOINT_CMD_A`（J1-J3）、`0x102 ARM_JOINT_CMD_B`（J4+底座） |
| Jetson → 广播 | 事件 | `0x010 SAFETY_CMD`（启动/停止/急停/清急停/清故障/软复位/同步） |
| 底盘 → Jetson | 100 / 10 Hz | `0x200 CHASSIS_VEL_FB`、`0x201 CHASSIS_DIAG` |
| 机械臂 → Jetson | 100 / 10 Hz | `0x210`+`0x211` 关节实测、`0x212 ARM_DIAG` |
| 底盘 ↔ 机械臂 | **1 kHz** | `0x030 XFER_CH_TO_ARM`、`0x031 XFER_ARM_TO_CH` |
| 故障上报 | 事件 | `0x020 EMCY_CHASSIS`、`0x021 EMCY_ARM` |
| 节点信息 | 上电 + 1 Hz | `0x230`、`0x231`（协议版本 + 固件构建标识） |

⚠️ 草案里的编号（`0x102` 急停、`0x300/0x301` 互发）**优先级是错的**：急停与故障帧的 ID 必须小于指令帧才能抢得过。v3 重新编号，映射表见 [`protocol.md`](PROTOCOL.md) §3。

**总线负载核算（按 v3 实际帧集重算）**：1 Mbps 下标准 8 字节帧 ≈108 bit ≈108 µs，含位填充最坏 ≈130 µs。
互锁 1 kHz × 2 帧 = 2000 帧/s ≈ **21.6 %～26 %**；上下行 6 帧 ×100/10 Hz ≈ 660 帧/s ≈ 7 %～9 %。合计 **≈ 29 %～35 %**，可用但余量有限。

- 若把臂的 4 个关节全量提到 1 kHz（草案原意），要 4 帧 @1 kHz → 负载直接翻倍到 ≈50 %。**提频前先算。**
- 两板 1 kHz 互发是设计规定（下位机之间 1 kHz），也是时基对齐与互锁通道。

## 3. 固件分层（两块板共用同一套层名）

自下而上，每层只依赖它下面一层；**跨层调用禁止**（例如通信层直接改 PWM）。

| 层 | 底盘模块 | 机械臂模块 | 实时性 | 单一写者的数据 |
| --- | --- | --- | --- | --- |
| **L0 外设** | CubeMX 生成的 `main.c/gpio.c/stm32f4xx_it.c/*_msp.c`、HAL | 同 | — | — |
| **L1 驱动** | `app_motor`（AT8236 双输入：方向/刹车/滑行）、`app_encoder`（硬件正交）、`app_oled`、`app_batt`、`app_watchdog` | **同一份源码**（`app_joint` 只是 `app_motor` 的别名 + 限位参数） | 调用即返回，不阻塞 | 原始计数 |
| **L2 实时控制** | `app_loop`：25 kHz ISR 宿主 → 1 ms 窗 M 法测速 → 定点 PI → 占空比刷新 | 同 + `app_traj`（关节轨迹插值，把 MoveIt 的 100 Hz 目标点铺成 25 kHz 位置参考） | **硬实时，25 kHz ISR，优先级最高，不受调度器影响** | 转速、占空比、位置累计 |
| **L3 运动学/解算** | `app_mecanum`：`(Vx,Vy,ωz)` → 四轮速度目标 | （无 IK）`app_limit`：关节限位/奇异规避的本地兜底 | 100 Hz，监督任务内 | 目标速度/目标角 |
| **L4 监督与安全** | `app_supervise`：命令解析、生命期超时、急停锁存、模式状态机、遥测计算、台架测试 | 同 | 100 Hz 任务 | 模式、故障码、enable |
| **L5 通信** | `app_can`：帧编解码 + CRC8 + RX 队列 + 1 kHz/100 Hz 发送节拍 | 同（帧集合不同） | 事件 + 定时任务 | 无（只搬运） |

### 为什么这么切

- **L2 是唯一硬实时层**，它的数据（计数、位置、占空比）由 ISR 独占写入，上层只读。上一轮已经踩实过这个约定（"编码器计数、位置累计全部归 ISR 所有，单一写者，监督器只读"），沿用。
- **L3 在两端不对称**：底盘是麦轮 IK（速度目标），机械臂是轨迹插值（位置目标）。把不对称性关在 L3，L1/L2/L4/L5 就能两端共用。
- **L4 与 L5 分开**：协议编解码是可单测的纯函数；安全状态机是行为逻辑。混在一起就会像上一轮那样"协议规格写在头文件注释里、没法单测"。

### FreeRTOS 任务映射（底盘）

| 任务 | 优先级 | 周期 | 说明 |
| --- | --- | --- | --- |
| （TIMx ISR，L2） | 硬件 2 | 40 µs | 25 kHz，不进调度器 |
| `Task_Control` | 6 | 100 Hz | L3 + L4 |
| `Task_CAN_Rx` | 5 | 事件（队列阻塞） | L5 收 |
| `Task_CAN_Tx` | 4 | 1 kHz | L5 发 `0x300`，每 10 拍发 `0x200` |
| `Task_Status` | 3 | 10 Hz | 喂 IWDG + 200 ms 刷 OLED |
| `Task_Debug` | 1 | 空闲 | SWD 邮箱 / 诊断 |

机械臂同构：`Task_Trajectory`（100 Hz，L3 插值 + 限位检查）取代 `Task_Control` 的运动学部分。

### 硬实时的量化预算（推断，需实测核对）

168 MHz 下 25 kHz 周期 = **6 720 个 CPU 周期**。四路测速 + 四次 PI + 四次 PWM 刷新 + CAN/编码器寄存器访问，必须控制在周期的 **≤ 35%（≈ 2 350 周期）**，否则 100 Hz 任务会被挤死。
核对手段：`DWT->CYCCNT` 打点或 ISR 入口翻转一个 GPIO 用逻辑分析仪量占空。ISR 里**禁止**：浮点、除法链、`printf`、阻塞队列、超过 8 字节的数组操作。

## 4. 两端共用一份驱动源码（工程决策）

**结论**：在仓库根新建 `platform/`（尚未创建，Phase B 第一步），放 L1/L2/L4/L5 的可共用部分，两个 CubeMX 工程的**顶层** `CMakeLists.txt` 用相对路径引用同一份源码：

```
code/
├── platform/                  ← 两端共用（不是第三个工程，不自己 build）
│   ├── Inc/  app_motor.h  app_encoder.h  app_loop.h  app_can.h  app_supervise.h  board_c30d.h
│   └── Src/  同名 .c
├── vehical_rak_chassis/       CMakeLists.txt 里 target_sources(+= ../platform/Src/*.c)
└── vehical_rak_arm/           同上
```

理由：两块板的电机/编码器/闭环/CAN/安全层是同一套物理结构（4 路 25 kHz 闭环 + CAN），**漂移风险远大于收益**——上一轮机械臂固件没落地，部分原因就是没有可复用的下位机基座。

选它的代价与约束（必须一起遵守）：

- 顶层 `CMakeLists.txt` 不会被 CubeMX 覆盖（`cmake/stm32cubemx/` 那份会），所以引用只写在顶层。
- `platform/` 里**不得 include 任何 CubeMX 生成的头文件**（`main.h`/`stm32f4xx_hal_conf.h` 除外，且只能靠工程侧提供）；板级差异（引脚、定时器号、通道号）全部走 `board_c30d.h` 这类**每工程各一份**的板级头，由工程侧在 include 路径里优先给出。
- IDE（CLion）需要能解析跨目录 include：顶层 `CMakeLists.txt` 里加 `target_include_directories(... ../platform/Inc)`，`compile_commands.json` 会自动带上，不需要额外配置。
- 备选方案（已否决）：**两边各拷一份** —— 会立刻漂移，历史上这类复制品最终都会走偏；**做成静态库 `.a`** —— 两端编译器/flags 必须严格一致，CubeMX 重生成时容易踩 ABI 坑，收益不比源码级共享大。

## 5. 实时闭环的技术口径

**设计规定：两块板都是 25 kHz 硬实时闭环。** 相关的定量事实与风险：

| 项 | 值 | 口径 / 状态 |
| --- | --- | --- |
| PWM 频率 | **25 kHz**（设计规定，两端一致） | 定时器时钟 = **168 MHz**（APB2 /2 → 84 MHz 总线，定时器 ×2）→ `ARR = 6720-1 = 6719`；上一轮记录的 `ARR=6720` 是周期计数（含 0），**别混用** |
| 控制 ISR 定时器（TIM6） | 25 kHz（40 µs），与 PWM 同频 | 注意 **TIM6 在 APB1**（总线 42 MHz → 定时器 **84 MHz**），所以它的 `ARR = 3360-1 = 3359`，与 PWM 定时器不同值 |
| 其他 ISR/时基 | TIM7 1 kHz 作 HAL 时基；SysTick 归 FreeRTOS | 25 kHz ISR **不调用任何 FreeRTOS API**，所以它可以比 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 更高（优先级数值更小）；而 CAN RX 这类要调队列的 ISR，优先级数值必须 **≥** 该阈值，否则内核会直接拦住 |
| 电机 | **MG513P30**（30:1 减速 + 编码器），底盘 4 台，机械臂 4 台**同型号** | 型号出自 `car2/README3.md:148`；"机械臂同型号"来自用户 2026-10-02 口述 |
| 编码器计数 | **61 600 计数/输出轴圈**（Motor A 手转一圈实测 61 602；理论 512×4×30 = 61 440） | 实测口径 = 硬件正交 **×4 倍频**后 |
| ⚠️ 计数口径差异 | 上一轮 README2 §3 写"15 360 计数/输出圈"，恰为 61 440 ÷ 4 | **我的推断**：那是**未倍频**（单通道）口径，写漏了限定词。本工程统一用 ×4 倍频口径，`board_c30d.h` 里只允许一个常数 |
| 测速 | 40 µs 单窗只有 ~6 计数（±16%）→ **1 ms 窗 M 法**（分辨率约 ±0.7%） | 台架物理限制，已验证 |
| 速度环 | 定点 PI，无浮点；`duty_q` 单位 0.01%，限幅 ±85% | 增益是上一轮估计值，本工程必须重新整定 |
| 起步 | 静摩擦门槛高（约 75% 才挣脱），需同拍强踢再交权给 PI | 台架实测 + 上一轮 H7 方案 |
| ⚠️ **25 kHz 出扭矩风险** | 台架期记录："10 kHz 是唯一验证过能让 AT8236 出扭矩的频率，25 kHz 试过发不出扭矩"（`car2/four-motor-sync/main.c:5-8`），而上一轮 H5–H7 又声称 25 kHz 跑到 3.00±0.01 圈 | **两条记录冲突，未裁决。** 设计目标仍是 25 kHz；首次上板必须用示波器/逻辑分析仪 + 带载实测确认 25 kHz 能否出额定扭矩。**若不能，是上报硬件/驱动限制并决策（换驱动、降频、提高 gate 驱动能力），不是擅自把频率改掉** |

| 6 | 关节角零位如何定（限位开关？人工示教？） | 决定 `ARM_JOINT_CMD_*` 的角度零点与 MoveIt 的 URDF 原点一致性 |

## 7. 落地顺序（分层驱动，不按"功能"排）

0. **先改时钟树：HSI → HSE 8 MHz。** 1 Mbps CAN 不能跑在 HSI 上（[`protocol.md`](PROTOCOL.md) §2、[`board-c30d.md`](BOARD-C30D.md) §6）。这一步在任何上总线工作之前做，否则后面调试会被"偶发错误帧"吞掉几天。
1. **L1 + L2 打样（底盘）**：4 路 PWM/编码器/25 kHz ISR/1 ms 测速/定点 PI，先在台架按键形态跑通（不带 CAN）。验收 = 四路同速收敛 + 落点精度 + **ISR 占用率实测** + **25 kHz 能否出扭矩**（第 5 节风险项）。
2. **把 L1/L2/L4/L5 抽进 `platform/`**（第 1 步就按可抽的形状写；两板硬件相同，共用没有例外）。
3. **L5 通信**：先跑 `python3 tools/can_check.py`（已在仓库里，实测可用）做参考实现与向量比对，MCU 侧用 `--c-header` 生成的 `docs/gen/can_protocol.h`，**不要在 C 里手写一遍帧表**。
4. **L4 安全**：生命期超时、急停锁存（含复位后仍锁存）、看门狗、`build_tag` 显示，全部在带载测试之前完成。
5. **L3 麦轮 IK + 标定**（轮径、`lx+ly`、每轮符号、B/C/D 各自计数常数）。
6. **机械臂**：先定第 6 节 #1/#2/#3 → 复用 `platform/` 的 L1/L2 → 只新写 `app_traj`/`app_limit` + 步进驱动模块。
7. **Jetson 端（`rak`）**：新增 CAN 节点（现有 `motor_stub` 只转 Twist，不带 Vy/enable/CRC/counter），并把 `CLAUDE.md`/`README.md` 里的 **CAN FD 与 G474/H743 表述改成实际三节点**（见 [`protocol.md`](PROTOCOL.md) §10）。
